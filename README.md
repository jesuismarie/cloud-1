# Cloud-1

## Introduction

Cloud-1 is the follow-up to the Inception project: instead of building the containerized infrastructure by hand on a local VM, the goal here is to **automate the deployment of an equivalent WordPress infrastructure on a remote cloud instance**. Provisioning the instance, hardening it, installing Docker, and deploying the application are all automated: Terraform provisions the instance via `make`, and Ansible then configures it and deploys the stack, so the whole thing can be stood up from scratch on any fresh Ubuntu 22.04 server without manual steps on the target itself.

## What is Terraform?

Terraform is a declarative infrastructure-as-code tool: instead of manually clicking through the AWS Console to create a server, you describe the desired end state (an EC2 instance, a security group, a key pair) in `.tf` files, and Terraform figures out what needs to be created, changed, or destroyed to get there. It tracks everything it manages in a state file, so re-running it is idempotent — if nothing changed, nothing happens. Here, Terraform owns everything up to "a reachable Ubuntu server exists"; Ansible takes over from there.

## What is Ansible?

Ansible is an agentless automation tool that connects to remote hosts over SSH and applies a declarative, idempotent set of tasks described in YAML (playbooks and roles). It is used here to provision the server, install Docker, configure the firewall, issue TLS certificates, and deploy the Docker Compose stack — all in a repeatable way that produces the same result whether run once or a hundred times.

## What is Docker Compose?

Docker Compose is a tool for defining and managing multi-container Docker applications. Using a `docker-compose.yml` file, you can configure your services, networks, and volumes in a declarative format. Here, Compose is not run manually — it is templated and triggered by the Ansible `deploy` role.

## Key Concepts

### Terraform Resource

A single infrastructure object Terraform is responsible for creating and managing — e.g. `aws_instance`, `aws_security_group`, `aws_key_pair`. Each resource block declares what it should look like; Terraform handles the actual API calls to AWS to make that true.

### Terraform Data Source

A read-only lookup against something that already exists, rather than something Terraform creates. `data "aws_ami"` resolves the current official Ubuntu 22.04 image ID from Canonical at plan time, instead of a hardcoded ID that would go stale or only work in one AWS region.

### Terraform State

Terraform's record of what it's already created and what those resources' real attributes are (IDs, IPs, etc.), stored in `terraform.tfstate`. This is how `terraform apply` knows the difference between "create a new instance" and "nothing changed, do nothing" on a second run — and why the state file itself is treated as sensitive and kept out of git alongside `secrets/` and `.env`.

### Terraform Variables

Inputs declared in `variables.tf` (region, instance type, SSH key path) and supplied via `terraform.tfvars` at apply time, rather than hardcoded — the same reasoning as `.env` for the application layer: one file holds the machine-specific values, separate from the code that consumes them.

### Ansible Role

A self-contained unit of automation (tasks, handlers, templates, files, defaults) responsible for one concern of the deployment — e.g. installing Docker, configuring the firewall, issuing certificates, or deploying the application stack. Splitting the playbook into roles keeps the automation maintainable and reusable across servers.

### Ansible Inventory

The `inventory/hosts.ini` file lists the target host(s) the playbook can run against, allowing the same automation to deploy to one server or several in parallel.

### Docker Image

A Docker image is a lightweight, standalone, executable package that contains everything required to run an application, including the code, runtime, libraries, environment variables, and configuration files.

### Docker Volume

A Docker volume is a mechanism for persisting data generated by and used by Docker containers. Volumes ensure WordPress files and database data survive a container restart or host reboot.

### Docker Secrets

Sensitive values (database passwords, WordPress admin/user passwords) are never stored in plaintext environment variables or committed to the repository. Each secret is mounted read-only inside its container as a file at `/run/secrets/<secret_name>`, generated locally before the Ansible run and never baked into images or logged.

## Project Structure

The project directory is structured as follows:

```
cloud-1/
├── infra
│   ├── configuration
│   │   ├── ansible.cfg
│   │   ├── group_vars/
│   │   ├── inventory
│   │   │   └── hosts.ini
│   │   ├── playbooks/
│   │   └── roles
│   │       ├── common/
│   │       ├── deploy/
│   │       ├── docker/
│   │       └── firewall/
│   └── provision
│       ├── main.tf
│       ├── output.tf
│       ├── providers.tf
│       ├── templates/
│       ├── terraform.tfvars
│       └── variables.tf
├── Makefile
└── srcs
    ├── docker-compose.yml
    ├── .env
    ├── requirements
    │   ├── nginx
    │   │   ├── conf
    │   │   │   └── default.conf
    │   │   ├── Dockerfile
    │   │   └── tools
    │   │       └── run_nginx.sh
    │   └── wordpress
    │       ├── Dockerfile
    │       └── tools
    │           └── run_wordpress.sh
    └── secrets/
```

- **infra/provision/**: Terraform — provisions the EC2 instance (`main.tf`), provider setup (`providers.tf`), inputs (`variables.tf`), and outputs (`output.tf`).
- **infra/configuration/**: Ansible — `ansible.cfg`, inventory, group vars, and one role per concern (`common`, `docker`, `firewall`, `tls`, `deploy`).
- **srcs/requirements/**: Custom-built NGINX and WordPress images; MySQL and phpMyAdmin use official upstream images with no Dockerfile.
- **srcs/secrets/**: Git-ignored credential files, shipped to the host as Docker secrets — never in `.env`, never committed.

## Usage

### Steps

1. Install the necessary dependencies on your control machine:

	```bash
	sudo apt update
	sudo apt install -y build-essential ansible gnupg software-properties-common curl
	```

	Terraform is not in Ubuntu's default repositories, so add HashiCorp's apt repository first:

	```bash
	wget -O- https://apt.releases.hashicorp.com/gpg | sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
	echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com $(lsb_release -cs) main" | sudo tee /etc/apt/sources.list.d/hashicorp.list
	sudo apt update
	sudo apt install -y terraform
	```

2. Clone the repository:

	```bash
	git clone https://github.com/jesuismarie/cloud-1.git
	cd cloud-1
	```

3. Configure the `.env` file:

	- Copy the example file and edit it:

		```bash
		cp srcs/.env_example srcs/.env
		```

	- It should look like this (no passwords here — those go in `secrets/`, see step 4):

		```
		USERNAME=xxxx
		DOMAIN_NAME=xxxx.xx.xx

		# certificate
		CERTS=/etc/nginx/ssl/xxxx.crt
		KEYOUT=/etc/nginx/ssl/xxxx.key

		# MYSQL SETUP
		MYSQL_USER=xxxx
		MYSQL_DATABASE=xxxx
		MYSQL_HOSTNAME=mysql

		# WORDPRESS SETUP
		WORDPRESS_TITLE=xxxx
		WORDPRESS_ROOT_USERNAME=xxxx
		WORDPRESS_ROOT_EMAIL=xxxx

		WORDPRESS_USER_USERNAME=xxxx
		WORDPRESS_USER_EMAIL=xxxx

		PMA_HOST=mysql
		PMA_ABSOLUTE_URI=https://xxxx.xx.xx/phpmyadmin/
		```

4. Create the secrets directory and populate it:
	- `secrets/` is excluded from git, so you need to create it yourself after cloning:

		```bash
		mkdir -p srcs/secrets
		echo -n "your-db-user-password"    > srcs/secrets/db_pass.txt
		echo -n "your-db-root-password"    > srcs/secrets/db_root_pass.txt
		echo -n "your-wp-admin-password"   > srcs/secrets/wp_root_pass.txt
		echo -n "your-wp-user-password"    > srcs/secrets/wp_user_pass.txt
		```

	- Each file should contain a single password with no extra formatting.

5. Configure AWS credentials:
	- Terraform authenticates as whichever AWS identity is configured locally — it never stores or requests credentials itself. If you don't have the AWS CLI yet:

		```bash
		sudo apt install -y awscli
		```

		The `awscli` package from Ubuntu's repositories is AWS CLI v1, which is all this project needs (`aws configure` and `aws sts get-caller-identity`).

	- In the AWS Console, create an IAM user for this project (avoid using root or an admin-access user) and scope it to EC2 only — the `AmazonEC2FullAccess` managed policy covers everything this project needs. Under that user's **Security credentials** tab, create an access key for **Command Line Interface (CLI)** use.
	- Configure the CLI with that key:

		```bash
		aws configure
		```

		You'll be prompted for the Access Key ID, Secret Access Key, a default region (use the same value as `aws_region` in `infra/provision/variables.tf`, e.g. `us-east-1`), and a default output format (`json`).

	- Verify it worked:

		```bash
		aws sts get-caller-identity
		```

		This should return your IAM user's account ID and ARN. `aws configure` stores credentials in `~/.aws/credentials`, outside the repository — never paste an access key or secret directly into any `.tf`, `.env`, or Ansible file.

6. Provision the cloud instance using the Makefile:

	```bash
	make
	```

	- This runs `ssh-key` (generates a local SSH key pair if one doesn't already exist), then `terraform init`, `plan`, and `apply` in `infra/provision/` to create the EC2 instance. The instance boots as a fresh Ubuntu 22.04 LTS-like server with an SSH daemon and Python installed; everything else (Docker, firewall rules, certificates) is installed by Ansible in the next step.
	- Note the instance's public IP from the Terraform output — you'll need it for the next step.

7. Configure the inventory:
	- Edit `infra/configuration/inventory/hosts.ini` with the IP (or hostname) of the instance you just provisioned, and the SSH key generated in step 6:

		```
		[cloud1]
		x.x.x.x ansible_user=ubuntu ansible_ssh_private_key_file=/path/to/key
		```

8. Run the Ansible playbook to configure the instance and deploy the stack:

	```bash
	ansible-playbook -i infra/configuration/inventory/hosts.ini infra/configuration/playbooks/main.yml
	```

9. Access the infrastructure:
	- Open `https://<your-domain-name>` in your browser to access the WordPress website.

### Additional Commands

**Provisioning (Terraform, via the Makefile):**

- Generate the SSH key pair, then init/plan/apply the instance (idempotent — safe to re-run):

	```bash
	make
	# or: make all
	```

- Run each Terraform step individually:

	```bash
	make ssh-key      # generate the SSH key pair if it doesn't already exist
	make init         # terraform init
	make plan         # terraform plan
	make apply        # terraform apply
	```

- Tear the instance down, then provision a fresh one:

	```bash
	make redeploy
	```

- Destroy the cloud instance:

	```bash
	make destroy
	```

- Destroy and remove all Terraform data:

	```bash
	make remove
	```

- Inspect current Terraform state, validate config, or generate a dependency graph:

	```bash
	make show
	make validate
	make format
	make graph
	```

**Local testing (Docker Compose only, bypasses Terraform/Ansible):**

- Bring the stack up directly on your own machine, for local testing without a cloud instance:

	```bash
	make local
	```

	- Creates the local WordPress/MySQL data directories, checks `srcs/.env` exists, then runs `docker-compose up -d --build`.

- Stop the local stack:

	```bash
	make down
	```

- Remove local containers, images, volumes, and data directories:

	```bash
	make clean-local
	```

- Clean and rebuild the local stack from scratch:

	```bash
	make re
	```

## Project Features

### Mandatory

- **Fully automated deployment**: `make` provisions the cloud instance via Terraform, and a single Ansible playbook then installs Docker, hardens the firewall, issues TLS certificates, and deploys the stack — no manual steps on the target server itself.
- **Portable**: The playbook can target any fresh Ubuntu 22.04 LTS-like instance with only SSH and Python present, and can deploy to several servers in parallel via the inventory.
- **Idempotent**: Running the playbook multiple times converges to the same working state instead of duplicating work or breaking the stack.
- **NGINX**: Provides secure HTTPS access using TLS (port 443), with URL-based routing to the correct site.
- **WordPress**: PHP-FPM configured for content management, built from a custom Dockerfile.
- **MySQL**: Backend database for WordPress, using the official upstream image.
- **phpMyAdmin**: Database administration UI, using the official upstream image, reachable only through the hardened stack.
- **Docker Secrets**: All passwords (database, WordPress admin/user) are handled via Docker secrets, mounted as files at `/run/secrets/`, never stored in `.env`, hard-coded, or baked into images.
- **Volumes**: Separate persistent storage for WordPress files and database data, surviving container recreation and host reboot.
- **Restart policy**: Services restart automatically if the server reboots.
- **Network**: Custom Docker network connecting all containers; direct external access to the database is blocked.
- **Firewall**: Only ports 80 (HTTP), 443 (HTTPS), and 22 (SSH) are reachable from outside — all other ports are blocked by the `firewall` role.
